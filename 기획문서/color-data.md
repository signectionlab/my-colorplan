## 1. 목적과 사용 원칙

이 문서는 색채교육에 사용하는 **콘텐츠 데이터의 기준**을 관리한다. `plan.md`는 학습 목표·기능, `design.md`는 화면 UX, `devlop.md`는 구현·저장 구조를 관리한다. 실제 Svelte/TypeScript 데이터 파일은 이 문서와 검증된 대응관계를 유지한다.

1. **기본색명**(예: 빨강), **계통색이름 또는 형용색명**(예: 선명한 빨강), **이미지 형용사**(예: 열정적인)를 혼동하지 않는다.
2. 먼셀 색상기호, KS A 0011 색이름, KS에서 차용한 톤, 웹 화면용 HEX는 서로 다른 정보다. 근사 HEX를 표준 측색값이라고 하지 않는다.
3. 이미지 형용사는 개인 경험, 문화, 업종, 주변색, 톤 등에 따라 달라지는 **연상 예시**이며 단정적인 심리 효과가 아니다.
4. STEP 1에서 선택한 색상·톤은 STEP 2에서 관찰·비교만 해서는 변경되지 않는다. STEP 4의 팔레트도 자동 변경하지 않는다.
5. 검증된 데이터와 미검증 후보를 구분해 표기한다. 표준 원문 확인 전에는 'KS 공식 형용색명'이라고 표시하지 않는다.

## 2. 기본색상 데이터 — 먼셀 10색상환

먼셀의 5기본색상(R, Y, G, B, P)과 5중간색상(YR, GY, BG, PB, RP)을 합친 10색상 순서다. 아래 영문은 기호 의미를 돕는 참고 표기이며 실제 앱의 `hueId`와는 아직 연결하지 않았다.

| 순서 | 기호 | 기본색명 | 영문 참고 | 형용사 데이터 키 제안 |
|---:|---|---|---|---|
| 1 | R | 빨강 | Red | `R` |
| 2 | YR | 주황 | Yellow Red | `YR` |
| 3 | Y | 노랑 | Yellow | `Y` |
| 4 | GY | 연두 | Green Yellow | `GY` |
| 5 | G | 초록 | Green | `G` |
| 6 | BG | 청록 | Blue Green | `BG` |
| 7 | B | 파랑 | Blue | `B` |
| 8 | PB | 남색 | Purple Blue | `PB` |
| 9 | P | 보라 | Purple | `P` |
| 10 | RP | 자주 | Red Purple | **실제 앱 ID `PR`** (먼셀 일반 표기 `RP`와 다름) |

**주의:** 기본 10색상환의 색상 범주를 특정 Munsell HVC 측정값이나 하나의 HEX로 일대일 고정하지 않는다. 기존 프로젝트의 색상·톤별 HEX 정의를 그대로 사용한다. 특히 앱은 자주의 ID와 화면용 기호에 `PR`을 사용한다. 기존 저장된 `hueId`를 바꾸지 말고 표준 참고 기호 `RP`를 별도 메타데이터로 관리한다.

### 무채색 (별도 처리)

| 기본색명 | 기호/분류 | 구현 참고 |
|---|---|---|
| 하양 | 무채색 | 현재 앱의 흰색 계열 데이터 확인 |
| 회색 | 무채색 | 밝은·중간·어두운 회색 단계가 있는지 확인 |
| 검정 | 무채색 | 현재 앱의 검정 계열 데이터 확인 |

무채색을 유채색 10종과 동일한 `hueId:toneId` 구조로 취급하는지는 실제 코드에서 확인한다.

실제 무채색 선택은 `hueId = 'N'`, `toneId = 'N9.5'` 등의 명도 라벨로 관리한다. `NEUTRAL_VALUE_STEPS`가 밝은 쪽부터 어두운 쪽으로 10개 근사 회색칩을 생성하며, `Wh`/`Bk`는 탐색 방향의 기준색으로 사용한다. 단계 이름은 `neutralGrayName`과 `neutralPickColorName`으로 정한다. 이 값은 UI 참고값으로 다룬다.

## 4. 형용색명(계통색이름) 후보 — STEP 2 활동 1

기본색명에 색의 명도·채도를 나타내는 수식어를 붙여 더 구체적인 색을 설명한다. 이 문서에서 '형용색명'은 학습자 친화적 UI 용어다. 표준 명칭을 설명할 때는 **계통색이름**이라는 용어를 병기한다.

| 한국어 수식어 후보 | 영문 참고 | 교육용 간단 설명 | 검증 상태 |
|---|---|---|---|
| 선명한 | vivid | 또렷하고 색의 기운이 강한 | `needs-verification` |
| 밝은 | light | 밝게 보이는 | `needs-verification` |
| 연한 | pale | 옅고 부드럽게 보이는 | `needs-verification` |
| 아주 연한 | very pale | 매우 옅게 보이는 | `needs-verification` |
| 진한 | deep | 깊고 강하게 보이는 | `needs-verification` |
| 어두운 | dark | 밝기가 낮은 | `needs-verification` |
| 탁한 | dull | 선명함이 낮아 탁하게 보이는 | `needs-verification` |
| 회색빛의 | grayish | 회색 기운이 느껴지는 | `needs-verification` |

위 8개는 **전체 KS 수식어의 확정 목록이 아니다.** 실제 앱은 아래 12개 기본 색조를 이미 사용 중이다. KS A 0011 원문의 정확한 적용 범위는 추가 대조해야 한다. 밝기·선명함에 대한 설명도 학습자용 간단 풀이이며 색도 경계 정의가 아니다.

### 4.0 실제 앱의 12개 톤 (`KS_BASIC_TONE_DEFS`)

출처: `src/data/munsell-brand-image.ts`. 이 명칭은 **앱의 기존 KS 차용 기본색조 UI 라벨**이며 각각의 `hueId:toneId`가 정확한 KS 계통색이름으로 검증되었다는 뜻은 아니다.

| `toneId` | 약어 | 영어 | 기존 한글 라벨 | 교육용 합성 예시 (빨강 선택 시) |
|---|---|---|---|---|
| `v` | v | Vivid | 선명한 | 선명한 빨강 |
| `s` | s | Strong | 강한 | 강한 빨강 |
| `dp` | dp | Deep | 진한 | 진한 빨강 |
| `dk` | dk | Dark | 어두운 | 어두운 빨강 |
| `p` | p | Pale | 연한 | 연한 빨강 |
| `lt` | lt | Light | 밝은 | 밝은 빨강 |
| `w` | w | Whitish | 흰 | 흰 빨강 (표준 표현 적합성 검증 필요) |
| `ltg` | ltg | Light grayish | 밝은 회색빛의 | 밝은 회색빛의 빨강 |
| `g` | g | Grayish | 회색빛의 | 회색빛의 빨강 |
| `dkg` | dkg | Dark grayish | 어두운 회색빛의 | 어두운 회색빛의 빨강 |
| `sf` | sf | Soft | 흐린 | 흐린 빨강 |
| `d` | d | Dull | 탁한 | 탁한 빨강 |

색상별 톤 HEX는 120개를 하드코딩한 값이 아니다. `tonesForHue(hue)`가 기준 HEX를 `approximateToneHex`의 흰색/검정 혼합·채도 조정 규칙으로 변형한다. 따라서 12×10개 칩은 **계산 결과이며 실제 KS/Munsell HVC 변환이 아니다**. 문서에 HEX 전체를 별도 중복 저장하지 말고 이 생성 규칙을 단일 소스로 유지한다.

### 4.2 무채색

- 하양, 회색, 검정은 유채색 톤 수식어를 기계적으로 합성하지 않는다.
- '밝은 회색', '어두운 회색' 등은 현재 무채색 단계와 KS 기준 대조 후 노출 여부를 결정한다.
- 검증 전에는 현재 앱에서 사용하던 기존 무채색 이름을 유지한다.

| `toneId` 전체와 순서 | 확인: `v,s,dp,dk,p,lt,w,ltg,g,dkg,sf,d` | 4.0절 참조 |
| 톤별 약어·한글 형용사 | 확인: 4.0절 | 기존 한글 라벨 유지 |
| `hueId:toneId`별 HEX | 생성 규칙 확인 | `tonesForHue` 계산값 사용, 교체 금지 |
| 무채색 ID/단계 | 확인: `N` + `N9.5`~`N1.5` 근사 10단계 | `NEUTRAL_VALUE_STEPS` 참조 |
| 톤별 KS 계통색명 대응 | 검증 필요 | KS A 0011 원문·색상 범위 대조 |

데이터 연결 시 권장 흐름: `기존 hueId` → `표준 10색상 기호` → `이미지 형용사`, `기존 toneId` + `색상·명도·채도 확인 결과` → `형용색명`. 기존 키와 저장값은 바꾸지 않는다.

### 5.1 STEP 2 코드 연결 상세

| 목적 | 기존 코드 | 권장 변경 |
|---|---|---|
| 선택 색 읽기 | `LearnScreen.svelte`의 `focusPick`, `focusKey` | 유지 |
| 대표 칩 | `.activity-act1 .hero-card` | 대표 이미지 형용사 1개를 hero 영역 중앙에 배치 |
| 색명/톤 표시 | `pickSummaryLabel`, `imagePickLabel` | 기존 표기는 유지하고 별도 교육용 형용색명 줄 추가 |
| 밝기 비교 | `brightnessVariants` | 계산·배치 유지. **톤 수식어를 붙이지 않음** (단순 근사 밝기 변형이므로) |
| 비슷한 톤 | `neighborToneSwatches` | 기존 한글 톤 라벨 유지, 검증 상태를 구분한 교육용 조합 색명 보조 표기 가능 |
| 비교 활동 | `compareToneOptionsForPick`, `compareMineSideView`, `compareOtherSideView`, `compareChoiceGaugeForPick` | UI·게이지·2지선다; `imageComparePairForPick`는 하위 호환·요약용 |
| 기록 | `learn.focusPickKey`, `learn.brandPickRecords` (`imageCompareSide`, `compareToneId`, 레거시 fit 필드) | 스키마 v2 유지; 활동 3·보조 탐색 UI는 LearnScreen에서 제외 |

**별도 문제:** `src/data/colors.ts`의 보조 탭 `adjective`에 '코랄·민트·아이보리·차콜'이 '형용색명 예시'로 소개된다. 이들은 `수식어 + 기본색명` 형식의 계통색이름과 다르므로, 활동 1에서는 이 목록을 형용색명 데이터로 재사용하지 않는다. 보조 탭을 정리하는 일은 추후 별도 UX 작업으로 둔다.

## 6. 단계별 사용 규칙

| 단계 | 사용 데이터 | UX / 저장 원칙 |
|---|---|---|
| STEP 1 내 브랜드 | 기본색명·색상칩·톤 | 현재 색상/톤 선택 흐름 유지 |
| STEP 2 활동 1 | 선택 색의 이미지 형용사, 기본색명, 확인된 형용색명 | 대표 형용사 1개를 hero 칩에 표시; HEX·밝기·비슷한 톤 유지 |
| STEP 2 활동 2 | 동일 계열 톤·명도 비교, 이중 게이지, `mine`/`other` 선택(미선택 허용) | STEP 1 pick·HEX 자동 변경 없음; `compareToneId`·`imageCompareSide`만 기록 |
| STEP 2 (레거시 UI) | fit·보조 탭 | `fitChoice`/`fitReason`·`unsure` compare는 저장·계획서만; LearnScreen 미편집 |
| STEP 4 내 팔레트 | 선택된 색·역할·비율 | 표준명을 과장하지 않고 기존 팔레트 색상 관리 유지 |
| STEP 6 계획서 | 선택 색·역할·비율·선택 이유 | 사용자가 선택한 이유와 색 정보를 혼동 없이 표시 |

### 저장·호환 원칙

- 형용사·형용색명은 우선 정적 콘텐츠에서 조회하는 **파생 표시 데이터**다. 기존 Project v2 저장 구조에 중복 저장하지 않는다.
- `learn.focusPickKey`, `learn.brandPickRecords`, `learn.interestIds`, `learn.reasons`와 JSON v2 호환을 보존한다.
- 새로운 색 설명을 추가하는 작업 때문에 STEP 1의 색 선택값 또는 STEP 4의 팔레트를 자동 수정하지 않는다.
- 데이터에 없는 색상이 들어올 경우 기존 색명·톤을 유지하고 표시 자체가 깨지지 않도록 한다.
